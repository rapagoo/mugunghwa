# 관절 모델 비교

2026-10-07. 기존 박스 모델/엔진을 보존하고 YOLOv8n-pose를 별도 생성한다.
현재 환경(Python 3.8, Ultralytics 8.3.0, TensorRT 8.0.1.6)을 업그레이드하지 않는다.

- 원본: 공식 Ultralytics assets v8.3.0의 yolov8n-pose.pt.
- 별도 폴더: Jetson repo/.runtime/pose-models (Git 제외).
- 입력: 1×3×480×640, opset 12, 정적 batch 1, FP16, workspace 512MiB.
- 출력: yolov8n-pose-480x640-fp16.engine. 기존 엔진 경로를 덮어쓰지 않는다.
- 빌더는 ONNX task=pose와 kpt_shape=[17,3] 메타데이터를 유지한다.
- 기존 엔진의 detect 태스크는 그대로 지원한다.

## 비교 원칙

모델을 저장하는 것과 실행하는 것은 별개다. 두 모델 파일을 보관해도 추론을 두 번 하지 않는다.
생성/비교는 GPU 프로세스 하나씩 순차 실행하고 종료 시 기존 웹 서비스를 다시 시작한다.
빌드·로딩·준비 시간을 안정 구간 추론 시간과 구분한다.

같은 640×480 영상 프레임을 두 엔진에 순차 입력하고 박스/ID/관절 관측과 평균·p95 처리 시간,
순수 추론 시간을 기록한다. 화면·파일 저장·Pi 통신은 오프라인 처리 측정에서 제외한다.
웹 출력 비용과 처리 간격/지연은 별도 표본으로 확인한다.
관절 신뢰도 0.5 이상 개수는 정답 주석 기반 관절 정확도가 아니다.
사람 수·가림·거리·정지 오탐·회전/팔 움직임 누락을 실제 장면으로 추가 검증한다.

## 웹 범위

포즈 엔진을 --model로 선택하면 박스와 관절을 같은 모델 결과에서 얻는다.
웹 미리보기에 신뢰도 0.5 이상 관절과 연결선을 그리고 API pose.visible_keypoints를 표시한다.
기존 움직임/정지 지시 시험은 여전히 박스 중심 기반이다. 포즈 화면 표시만으로
관절 기반 탈락 판정을 완성했다고 표현하지 않는다.
확인 중 새 문제가 생기면 troubleshooting.md TS-VISION-008을 갱신한다.

## 관절 웹 미리보기 선택/복귀

동시에 GPU 추론 웹 서버를 두 개 실행하지 않는다. 기존 서비스와 포즈 비교는 같은 서비스에서
모델 경로만 선택한다. 기본 /etc/systemd/system/mugunghwa-web.service는 기존 박스 엔진이다.
비교 시 deploy/pose-preview.conf를 /run/systemd/system/mugunghwa-web.service.d/pose-preview.conf에
설치하고 daemon-reload/restart 한다. /run override는 재부팅하면 사라져 기본 박스 엔진으로 돌아간다.
현재 활성 모델은 웹의 관절 검출 비교 안내와 /api/vision의 pose.enabled로 확인한다.

기존 박스 엔진으로 복귀할 때는 아래를 Jetson에서 실행한다. 지정한 비교 파일 한 개만 제거한다.

```bash
sudo rm -f /run/systemd/system/mugunghwa-web.service.d/pose-preview.conf
sudo systemctl daemon-reload
sudo systemctl restart mugunghwa-web.service
```

저장한 구역/결승선과 기존 엔진, 비밀 DB 설정은 이 선택으로 덮어쓰지 않는다.
서비스 재시작은 시험 후보/추적 ID를 초기화한다. 엔진 준비 시간이 있으므로 재시작 직후
준비 중 화면을 안정 구간 FPS와 섞지 않는다.

## 2026-10-07 측정 결과

원본 960×540 사용자 영상에서 비율을 유지해 640×360으로 축소하고 위아래 60px를 채운
별도 640×480 H.264 시험 파일을 사용했다. 이 파생 파일은 596프레임이며 원본 598프레임과
같은 파일이 아니다. 원본/기존 변환 파일은 변경하지 않았다. 두 모델에는 같은 596프레임을 입력했다.
실제 모델 텐서는 모두 1×3×480×640, 신뢰도 0.35, ByteTrack, 준비 5회 제외,
GUI/웹 JPEG/네트워크/파일 출력 시간 제외, GPU 추론 프로세스는 순차 실행했다.
ROI/결승선 설정은 이 비교에 적용하지 않았다.

| 항목 | 기존 검출 FP16 | 관절 FP16 |
|---|---:|---:|
| 전체 처리량 FPS | 17.22 | 17.17 |
| 전체 평균 ms | 58.06 | 58.24 |
| 전체 p95 ms | 60.40 | 59.71 |
| 순수 추론 평균 ms | 40.10 | 40.75 |
| 사람 검출 프레임 | 556/596 | 485/596 |
| 추적 ID 포함 프레임 | 551/596 | 437/596 |
| 검출된 사람의 평균 관절 수(conf ≥0.5) | 해당 없음 | 16.51/17 |
| 측정 프로세스 최대 RSS KiB (준비/로딩 포함) | 2,929,080 | 2,881,012 |

이 조건에서 관절 처리량 감소는 약 0.3%였다. 다만 사람 검출은 71프레임 적었으므로
속도만 보고 기존 검출을 대체하지 않는다. 정답 주석이 없어 위 수치를 정확도라고 부르지 않는다.
관절 신뢰도/개수도 위치 정확도와 미세 움직임 감지의 증거가 아니다. 먼 거리·가림·임계값의
영향은 개별 프레임 비교와 실제 웹캠 시험으로 확인할 계획이다.
RSS는 프로세스 지표이며 GPU 전체 메모리/장비 RAM 최고치와 동일하지 않다.

별도 빈 웹캠 장면: 640×480 MJPEG 240프레임, 8.061초 촬영. 두 모델 모두 사람 0회.
기존 19.16FPS/평균52.18ms/p95 54.13ms, 관절18.75FPS/평균53.33ms/p95 55.74ms.
이 장면은 사람/관절 정확도 검증에 사용하지 않는다.

엔진 생성은 7분24.68초, 빌드 프로세스 최대 RSS 1,507,564KiB였다. 관절 엔진 약19MB,
.pt+ONNX+engine+로그 폴더 합계 약38MB, 시작 시 디스크 여유 약25GB였다.
파일을 저장하는 것 자체로 두 엔진이 동시에 실행되는 것은 아니다.

산출물은 Jetson repo/.runtime/pose-benchmark/person-{detect,pose}.json 및
동일 접두사의 .frames.jsonl/.log, 자원 측정 person-{detect,pose}-resources.txt이다.
사용자 영상·좌표 증거·모델·엔진은 Git에 추가하지 않는다.

자동 테스트 28개 통과: pose/detect 메타데이터, 잘못된 입력 크기/태스크,
빈 관절 결과의 가짜 인원 제거, 박스-관절 대응을 포함한다.

## 실시간 웹 확인

2026-10-07 임시 /run drop-in 적용 후 서비스 active와 pose.enabled=true 확인.
실제 웹캠에서 사람1명, 구역 버전1, 관절13개 API 표본 및 브라우저16~17개 표시,
파란 관절 연결선/박스/MJPEG를 확인했다. 웹 표본 검출 간격62~70ms,
최근300회 평균65.6ms는 장시간/다인 벤치마크나 전체 카메라→브라우저 지연이 아니다.
기존 엔진은 백업 파일과 cmp 일치를 확인했다.
기존 사람 검출 엔진을 동시에 실행하지 않으며, 기본 서비스 파일은 변경하지 않았다.
관절 기반 움직임 판정은 미연결이다. 실제 웹캠 정지 오탐·몸 회전/팔 움직임·가림·다인
검증과 검출 신뢰도 조정 후 채택 여부를 결정한다.
