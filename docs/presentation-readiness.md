# 발표 촬영 전 코드 점검 · 2026-10-12

대상: `pose-comparison`의 `7f6ed7d` (팀원 펌웨어 PR #1 병합 포함).
사용자가 이전 전체 게임 흐름 검증 완료를 보고한 것은 유지한다.
이번 점검은 소스와 발표 폴더의 인계·사실검증·코드분석 문서를 대조한 정적 분석이다.
장비 실행, 게임 START, 음원 재생, 펌웨어 빌드/업로드, 새 성능 측정은 하지 않았다.
로컬 분석을 위해 병합된 커밋까지 fast-forward했고 기능 소스는 수정하지 않았다.

## 판단

전체 장치 사진과 발표용 배선·LCD 확대 사진 촬영은 시작해도 된다.
새 기능이나 모델 교체는 필요하지 않다. 최종 시연 영상은 아래 통신 안정성 보완과
동일 버전 반복 리허설 후 촬영하는 것을 권한다.
발표 폴더의 촬영 목록(장치, 설정 화면, 관절 판정, 음원/회전 순서, LCD/웹/DB)은 현재 구현과 맞는다.

## 촬영 전 우선 보완 권고

### 1. STM32 수신 메시지 보존 (높음)

- `server_parser.c:316`에서 최초 개행만 찾고 `:356`에서 UART 수신 버퍼 전체를 지운다.
  예를 들어 `+IPD,길이:[PI]COUNT@2@0@0\n[PI]TIME@20\n`을 한 번에 받으면
  COUNT만 파서에 넘기고 뒤의 TIME은 버리는 실행 경로다. 별도 +IPD가 함께 쌓여도 잔여분을 보존하지 않는다.
- `esp01.c:29`의 AT 호출도 같은 `cb_data` 전체를 지운다. COUNT/TIME 적용 ACK 송신과
  10초 주기 상태 조회가 아직 처리하지 않은 서버 패킷을 지울 수 있다.
- Pi는 COUNT/TIME을 연속 전송하고 모터 명령도 같은 연결로 보낸다.
  단일 메시지 시험 성공과 별개로 LCD 누락·모터 완료 대기가 간헐적으로 생길 수 있다.
  실제 과거 장애의 원인이 이것이었다고 확정하지는 않는다.
- 권고: UART 수신을 보존하는 버퍼에서 +IPD 길이만큼 분리하고, TCP payload의 개행 메시지를
  누적/반복 처리한다. AT 응답과 서버 payload를 분리하고 송신 시 수신 데이터를 초기화하지 않는다.
- 확인할 시험(미실행): COUNT+TIME+MOTOR 연속/묶음 수신, 메시지 분할 수신,
  ACK 송신 및 상태 조회와 다음 명령 수신이 겹칠 때 모두 처리되는지 확인한다.

### 2. Pi Bluetooth 중계의 경계 처리 (중간)

- `bluetooth_client.c:103`의 `char msg[100]`에 최대100바이트를 읽고,
  `:133`에서 `msg[total]=0`을 쓰므로 정확히100바이트가 개행으로 끝나면 배열 밖에 쓴다.
  개행 없이100바이트가 차면 다음 read 길이가0이 되어 끊김으로 처리된다.
- 현재 정상 ACK는100바이트보다 짧아 이 조건을 보통 만들지는 않는다.
  다만 긴 입력/읽기 오류 처리, TCP/Bluetooth 부분 write 및 재접속을 보완할 여지가 있다.
- 권고: 상한을 넘지 않는 개행 누적 처리와 초과 길이 폐기/복구, 전체 송신 함수를 적용한다.
  중계 종료·재시작 운영 절차도 확정한다. 촬영 전에 보완하면 좋으나 STM 수신보다 우선순위는 낮다.

### 3. STM32 중복 회전 명령의 완료 응답 (중간)

- DIRECT_MODE=1이며 이동 완료는500ms 경과로 처리한다.
- `servo_set_angle()`은 PWM 목표를 설정하는 즉시 `current_angle`을 바꾼다.
  trigger의 이미 도착 판정은 상태 또는 `current_angle`을 확인한다.
  이동 중 같은 방향의 명령이 다시 오면500ms 경과 전에 완료 응답/도착 상태로 바뀔 수 있다.
- 정상 Pi 흐름은 완료를 기다리므로 매번 발생하는 문제는 아니다.
  중지/복귀 반복 요청과 명령 중복에 대한 보완 권고다.
- 권고: 이미 도착 여부는 IDLE_REAR/HOLD_AT_FRONT 상태로 판단하고, 같은 방향 이동 중이면
  기존 완료 시점을 유지한다. 반대 방향 명령에는 PWM 목표와 완료 대기를 다시 설정한다.
  회전 각도 센서는 없으므로 보완 후에도 응답은 펌웨어 처리 완료 기준이다.

## 추가 개발보다 최종 확인이 필요한 부분

| 항목 | 현재 근거 | 최종 확인 |
|---|---|---|
| 참가자·통과·탈락·타이머 | 구현 및 기존 모의/사용자 흐름 검증 | 동일 버전으로1명/2명, 실제 시연 시간180초 종료까지 |
| 총소리0.25초 간격 | 모의 시계 시험 통과 | 실제2~3명 동시 탈락 청음과 추론 지연 확인 |
| 구호·인형·정지 판정 | 사용자 흐름 검증 완료 | 촬영 장소에서 실제음원 종료→회전→판정 순서 기록 |
| DB·웹·양 LCD | 구현과 과거 표시 시험 | 같은 경기ID의 참가자·결과·시간이 일치하고 종료 기록이 남는지 |
| 재시작·무선 | 복귀 잠금과 재시도 구현, 과거 단절 기록 | 재부팅 후 웹/연결기, STM 재접속, 중계 실행, HOME 확인 |
| 발표 성능 수치 | 별도 저장 영상 FP32/FP16 비교 기록 | 현재 관절 게임 전체 FPS로 표현하지 않기 |

효과음은 여러 ffplay 프로세스가 잔향을 겹치는 방식이다. 실제 Jetson 부하와 청음 간격은
이번 분석에서 측정하지 않았으며 원본 길이나 예약 간격만으로 성능을 확정하지 않는다.
재식별·가림·얼굴만의 움직임·구역 이탈 뒤 판정 공백은 기존 한계로 유지한다.
시연 전 새 모델이나 재식별 기능으로 범위를 확대하기보다 전신이 보이는 촬영 구도를 확정한다.

## 마무리 순서

1. 장치 전체·보드·배선 사진은 지금 촬영한다.
2. STM 수신 안정성 우선 보완, 필요한 중계/서보 경계 처리 수정 후 해당 버전을 고정한다.
3. 한 번은180초 만료, 한 번은 통과/움직임 탈락으로 조기 종료, 한 번은 중지 후 재시작을 확인한다.
   총소리0.25초와 DB·웹·LCD 비교를 이 경기들에 함께 포함한다.
4. 재부팅 후 시작 절차를 한 번 리허설하고 코드 커밋·엔진·설정 백업을 확인한다.
5. 정상 경기 시연 영상을 촬영하고 실제 장면을 발표 초안에 넣는다.

사진/사용자 영상/음원은 Git에 추가하지 않는다. 기존 발표 폴더는 이번 분석에서 수정하지 않았다.
