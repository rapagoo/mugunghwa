# 무궁화꽃이 피었습니다 통신 시퀀스 및 라우팅 명세서

갱신: 2026-10-07. 상태: **설계 합의안·게임 전체 흐름 구현 전**.
사용자가 제공한 기존 명세서에 Pi 시간 제어와 방향별 회전 완료 응답을 반영했다.
현재 COUNT 테스트 구현은 [기존 통신 규격](protocol.md), 관절 시험은
[관절 움직임 시험](pose-motion-trial.md)을 참고한다. 이 문서를 작성했다고 아래 흐름이
이미 장비에 구현된 것은 아니다.

후속 한 회차 자동 시험 구현/단계 통지 확인 번호·실행 방법은
[자동 시험](cycle-trial.md)에 기록한다. 음원·랜덤·전체 게임 흐름은 여전히 미구현이다.

## 1. 역할과 메시지 경로

| 구성요소 | 역할 |
|---|---|
| Pi TCP 서버 | 로그인한 클라이언트 사이 목적지 중계, 발신자 헤더 부착 |
| Pi C 제어 클라이언트 (`PI`) | 게임 단계·타이머·랜덤 시간·최종 결과 관리, STM 명령, Jetson 단계 통지 |
| Jetson Python 클라이언트 (`JETSON`) | 참가자 영상 관측, 정지 중 움직임/결승선 통과 후보 생성·Pi 보고 |
| STM32 (`STM`) | 시작/중단 버튼 보고, 요청 방향으로 인형 회전, 방향별 완료 응답, LCD 표시 |
| Bluetooth 중계/Arduino (`ARD`) | Pi가 전달한 인원수·게임 정보 표시 |

이하 **Pi**는 게임 로직을 수행하는 **Pi C 제어 클라이언트**를 뜻한다.
모든 장비 간 메시지는 Pi TCP 서버를 경유한다. STM이 Jetson으로 직접 완료 응답을
보내거나 서버가 랜덤 타이머/게임 단계를 결정하지 않는다.
STM의 자율 랜덤 대기·자동 앞뒤 반복은 제거하고 Pi의 회전 명령을 수행한다.

## 2. 패킷 규칙과 회전 명령

- 실제 로그인 ID는 `PI`, `JETSON`, `STM`, `ARD`이며 대소문자를 구분한다.
- 송신 헤더: `[수신자ID]명령@필드`.
- 서버 중계 후 수신 헤더: `[발신자ID]명령@필드`.
- 각 게임 메시지 끝에 실제 LF(`\n`)를 붙인다. TCP/UART의 읽기 단위와 패킷 경계를
  동일하게 가정하지 않고 LF까지 누적한다.

방향별 명령/완료 형식은 다음으로 합의한다. 완료의 `OK`는 맨 뒤에 붙인다.

| 의미 | 송신 측 입력 | 최종 수신 문자열 |
|---|---|---|
| Pi가 앞보기 요청 | `[STM]MOTOR@FRONT` | STM: `[PI]MOTOR@FRONT` |
| STM이 앞보기 완료 보고 | `[PI]MOTOR@FRONT@OK` | Pi: `[STM]MOTOR@FRONT@OK` |
| Pi가 뒤보기 요청 | `[STM]MOTOR@REAR` | STM: `[PI]MOTOR@REAR` |
| STM이 뒤보기 완료 보고 | `[PI]MOTOR@REAR@OK` | Pi: `[STM]MOTOR@REAR@OK` |

STM은 AT 송신 성공이나 회전 명령 접수만으로 OK를 보내지 않고 회전 완료 후 전송한다.
완료가 센서 확인인지 서보 구동 대기 시간 경과인지 팀원과 구현 기준을 맞춘다.

## 3. 단계별 통신 시퀀스

### Step 1. 게임 시작과 참가자 확정

1. STM 시작 버튼 → STM이 Pi에 `[PI]START` 송신.
2. Pi는 시작 가능한 상태인지 확인하고 Jetson에 `[JETSON]START` 송신.
3. Jetson은 시작 시점의 구역 안 참가자를 관측하고 초기 정보를 Pi에 보고한다.
   START를 STM/ARD에 그대로 재전송하지 않는다.
4. Pi는 초기 정보를 검증해 게임 참가자/인원수를 확정하고 STM·ARD에
   `[STM]COUNT@total@pass@fail`, `[ARD]COUNT@total@pass@fail`를 각각 송신한다.
5. 초기 참가자 준비가 끝나면 이동 허용 및 첫 음원 재생 단계로 진행한다.
   초기 인형 방향이 뒤보기인지 확인하고 필요하면 REAR 요청/완료를 먼저 수행한다.

기존 COUNT 테스트 경로는 Jetson `[PI]COUNT@...` → Pi 수신 `[JETSON]COUNT@...`
→ Pi 검증/보드 전달이다. 최종 게임은 프레임별 검출 수를 곧바로 참가자 누적 수로 쓰지 않는다.
참가자 번호·추적ID 대응과 개별 결과 보고 필드는 후속 구현에서 확정한다.

### Step 2. 음원 재생과 앞보기 요청

1. 이동 허용 상태에서 지정한 “무궁화 꽃이 피었습니다” 음원을 재생한다.
2. 음원 재생 종료 시 Pi가 STM에 `[STM]MOTOR@FRONT`를 송신한다.
3. Pi는 **앞보기 완료 대기** 상태가 된다. 이때 Jetson 움직임은 아직 허용한다.
4. STM은 인형을 앞으로 돌린 뒤 `[PI]MOTOR@FRONT@OK`를 송신한다.
5. Pi가 `[STM]MOTOR@FRONT@OK`를 수신하면 Jetson에 정지 판정 시작을 통지하고
   Pi 자신의 랜덤 정지 타이머를 시작한다.
6. Jetson은 통지 이후의 관절 자세를 기준으로 정지 중 움직임 판정을 시작한다.
   별도0.7초 유예는 적용하지 않는다. 통신/처리 지연은 통합 시험에서 측정한다.

음원 재생 담당은 Pi로 두는 설계 방향이며 파일 위치·스피커 연결·재생 방식은 미확정이다.
다른 장치가 재생하게 되면 재생 종료를 Pi에 보고하는 메시지를 추가로 합의해야 한다.

### Step 3. 정지 유지와 결과 보고

1. **랜덤 유지 시간은 Pi C 클라이언트가 결정하고 관리한다.** 시작 기준은
   Pi가 앞보기 완료 응답을 정상 수신한 시점이다. 랜덤 범위는 추후 설정한다.
2. Jetson은 움직임/통과 관측 후보를 Pi에 보고한다.
3. Pi는 경기 단계·참가자 상태·중복 여부를 검증한 뒤 통과/탈락 결과와 누적 인원수를 확정한다.
4. 인원수가 바뀌면 Pi가 STM·ARD에 COUNT를 각각 전달하고 웹/DB에도 확정 상태를 반영한다.

후보→실제 탈락/통과 적용은 아직 미구현이다. 현재 웹 관절 후보를 바로 최종 결과로 취급하지 않는다.
COUNT는 현재 누적값이며 증감 명령이 아니다. STOP 구간의 결승선 통과/움직임 동시 발생
우선순위 등 세부 규칙은 후속 합의가 필요하다.

### Step 4. 뒤보기 요청과 이동 재개

1. Pi 랜덤 타이머가 끝나면 Pi가 STM에 `[STM]MOTOR@REAR`를 송신한다.
2. Pi는 **뒤보기 완료 대기** 상태가 된다. 완료 전까지 Jetson 정지 판정은 유지한다.
3. STM은 인형을 뒤로 돌린 뒤 `[PI]MOTOR@REAR@OK`를 송신한다.
4. Pi가 `[STM]MOTOR@REAR@OK`를 수신하면 Jetson에 이동 허용을 통지한다.
5. Jetson은 정지 중 움직임 판정을 종료하고 이동 허용 단계로 전환한다.
6. 게임 종료 조건에 해당하지 않으면 다음 음원 재생으로 이어간다.

기존 문서의 “STM이 랜덤 시간 후 자율 회전하고 MOTOR@REAR를 통지” 흐름은 사용하지 않는다.
REAR는 Pi의 명령이며, STM의 완료 응답은 반드시 MOTOR@REAR@OK로 구분한다.

### Step 5. 게임 중단

1. STM 중단 버튼 → `[PI]STOP` 송신.
2. Pi는 게임 진행/랜덤 타이머를 중단하고 STM·JETSON·ARD에 각각 STOP을 송신한다.
3. 진행 중 회전의 처리와 재시작 방식은 STM 팀원과 합의한다.
4. STOP을 RESET으로 해석하지 않는다. 리셋은 별도 동작/명령이며 결과 보존·타이머 초기화
   범위와 정상 종료 조건(시간 만료/전원 통과 또는 탈락)은 후속 확정한다.

## 4. Jetson 단계 통지와 라우팅 요약

STM 완료 패킷을 Jetson에 그대로 전달하기보다 Pi가 게임 단계로 해석해 통지한다.
아래 `PHASE@STOP`, `PHASE@MOVE`는 **이번 문서의 설계 제안이며 후속 코드에서 구현할 형식**이다.
STM 방향별 완료 응답 형식과 구분한다.

| 발신자 | 서버에 송신하는 문자열 | Pi C 클라이언트 처리/최종 수신 |
|---|---|---|
| STM | `[PI]START` | 시작 확인 → Jetson에 `[JETSON]START` |
| Pi | `[STM]MOTOR@FRONT` | STM 수신 `[PI]MOTOR@FRONT` |
| STM | `[PI]MOTOR@FRONT@OK` | Pi 수신 `[STM]MOTOR@FRONT@OK` → 정지 타이머/Jetson 통지 |
| Pi | `[JETSON]PHASE@STOP` | Jetson 수신 `[PI]PHASE@STOP` → 기준 자세/정지 판정 |
| Pi | `[STM]MOTOR@REAR` | STM 수신 `[PI]MOTOR@REAR` |
| STM | `[PI]MOTOR@REAR@OK` | Pi 수신 `[STM]MOTOR@REAR@OK` → Jetson 이동 허용 통지 |
| Pi | `[JETSON]PHASE@MOVE` | Jetson 수신 `[PI]PHASE@MOVE` → 움직임 허용 |
| Jetson | `[PI]COUNT@total@pass@fail` (기존 시험) | Pi 검증 → STM/ARD에 각각 COUNT |
| Pi | `[STM]COUNT@...`, `[ARD]COUNT@...` | 두 보드는 각각 `[PI]COUNT@...` 수신 |
| STM | `[PI]STOP` | Pi 중단 처리 → STM/JETSON/ARD에 각각 STOP |

서버의 단순 중계와 Pi 클라이언트가 생성하는 명령을 구분한다.
“두 보드에 브로드캐스트”는 Pi 클라이언트가 목적지별 패킷을 두 번 전송한다는 의미다.

## 5. 응답 처리와 남은 합의

- Pi는 STM에서 온 응답만 회전 완료로 인정하고, 현재 기다리는 방향과 일치하는 OK만 처리한다.
  예: 앞보기 대기 중 REAR@OK로 정지 판정을 시작하지 않는다.
- 같은 대기 상태를 두 번 완료 처리하지 않는다. 중단된 게임의 OK로 진행을 재개하지 않는다.
- OK가 없으면 다음 단계를 임의로 시작하지 않는다. 완료 대기 제한 시간·실패 표시·재시도는 후속 결정한다.
- 방향만으로는 이전 회차에서 늦게 온 같은 방향 응답을 완전히 구별할 수 없다.
  회차 번호/요청 번호 추가는 후속 합의 사항이며 현재 MOTOR 필드에 임의로 추가하지 않는다.
- 음원 파일/재생 장치, 랜덤 시간 범위, 게임 제한 시간, 참가자/결과 후보 필드,
  STOP/RESET/정상 종료, DB 저장·웹 표시 상세는 아직 구현/검증이 필요하다.

## 6. 검증 순서

1. Pi 서버를 켜고 수동 클라이언트에서 FRONT/REAR를 각각 송신하여
   STM 회전·방향별 OK 목적지PI를 확인한다.
2. Pi C 클라이언트가 OK를 처리하고 랜덤 타이머/다음 회전을 자동 진행하는지 확인한다.
3. Pi의 단계 통지에 Jetson 웹 정지/이동 상태가 바뀌고 후보가 Pi에 도착하는지 확인한다.
4. 음원 종료부터 인형 완료·정지 판정·뒤보기 완료까지 실제 통합 시연을 수행한다.

수동 통신 성공을 자동 제어/관절 정확도/실제 탈락 처리 완료로 간주하지 않는다.
