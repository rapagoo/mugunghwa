## 공통 조건과 지표

측정 장비는 Jetson Nano(Tegra X1), L4T R32.6.1, MAXN 전력 모드다.
YOLOv8n, PyTorch FP32/CUDA, ByteTrack, 사람 클래스, 신뢰도 임계값 0.35를 사용했다.
환경은 Python 3.8.10 / PyTorch 1.13 계열 / Ultralytics 8.3.0이다.
원본은 `20261006_141148.mp4`: 1920×1080 HEVC, 598프레임, 약 10.06초의 비디오 스트림,
평균 약 59.43fps다. 한 사람이 복도에서 카메라 쪽으로 이동하는 영상이다.

입력 영상 해상도와 `imgsz`는 다르다. 전자는 디코딩할 원본 크기이고 후자는 모델 전처리 목표 크기다.
`imgsz=640`은 1080p 원본 디코딩 비용을 줄이지 않는다.

- **처리 FPS**: 입력 읽기·전처리·추론·추적 등 지정 측정 범위의 초당 처리 프레임 수.
- **순수 추론 시간**: YOLO가 보고한 GPU 모델 계산 시간. 전체 처리 시간과 구분한다.
- **검출 갱신 간격**: 연속 검출 결과 완료 사이의 실제 시간.
- **결과 지연**: 프레임 전달부터 검출 결과가 완료될 때까지의 시간. 갱신 간격과 다르다.
- **표시 FPS**: 재생 창에 제출한 프레임 수. VNC 원격 단말에서 실제 보이는 FPS를 직접 측정한 값은 아니다.
- **사람 검출 프레임**: 사람 박스가 있는 프레임 수. 정답 주석과 대조한 일반 정확도 수치가 아니다.

### TS-VISION-001

**증상:** VNC에서 원본 영상의 사람 검출 화면이 매우 느려 보였다. 약 4fps라면 실제 게임도
같은 속도로 동작하는지, VNC가 원인인지 확인이 필요했다.

**조사:** 기존 검출 창을 종료하고 GPU 사용·MAXN 모드를 확인했다.
VNC 활성/일시 중지, GUI·매 프레임 JPEG 저장 유무, 영상/실제 웹캠을 분리해 측정했다.
각 조건은 준비 5프레임을 제외한 20프레임의 짧은 표본이다. Pi 통신은 포함하지 않았다.

| 입력과 출력 조건 | 모델 입력 | 전체 처리 FPS |
| --- | --- | ---: |
| 1080p 영상, VNC 활성, GUI + JPEG 저장 | 640 | 3.91 |
| 1080p 영상, VNC 활성, 화면·저장 없음 | 640 | 5.46 |
| 1080p 영상, VNC 중지, 화면·저장 없음 | 640 | 5.56 |
| 1080p 영상, VNC 중지, 화면·저장 없음 | 320 | 5.49 |
| 실제 640×480 웹캠, VNC 중지, 화면·저장 없음 | 640 | 11.55 |
| 실제 640×480 웹캠, VNC 중지, 화면·저장 없음 | 320 | 15.38 |

**원인과 근거:** 화면 없는 원본 영상 640 조건에서 프레임 읽기/디코딩 약 104.6ms,
검출·추적 호출 약 75.1ms, 순수 GPU 추론 약 57.3ms였다.
GUI + JPEG 조건의 출력 비용은 약 50.8ms였다.
VNC를 중지한 차이는 5.46→5.56fps로 작았다. 이 조건에서는 원본 읽기/디코딩과 출력 비용이 컸다.
웹캠 640의 프레임 읽기는 약 1.4ms, 순수 추론은 약 68.7ms였다.
웹캠과 원본 영상은 해상도·압축·입력 경로가 다르므로 차이를 해상도 하나의 효과로 단정하지 않는다.

**설명 정정:** 처음 설명했던 약 200~230ms를 순수 추론 시간으로 해석하면 안 된다.
입력·처리 단계와 함께 관측된 시간이었고, 분리 측정한 순수 GPU 추론은 위 수치다.

**조치:** 화면과 파일 저장을 성능 측정에서 분리하고, 영상 해상도/코덱 변환을 비교했다(TS-VISION-003).
VNC는 비교 때만 일시 중지 후 복구했다. 카메라 경로의 최종 속도는 별도 검증한다.

**남은 일:** 여러 사람·장시간 실행에서 평균/p95 지연, 온도·메모리, Pi·MCU 최종 반응 시간을 측정한다.
이 짧은 표본으로 시연 성능을 확정하지 않는다.

**근거:** [속도 측정과 실행 조건](game-camera-setup.md#처리-속도-측정-2026-10-06),
로컬/Jetson `.runtime/benchmark-vision.json`.

### TS-VISION-002

**증상:** 속도를 위해 모델 입력을 320으로 줄였더니 영상 초반의 멀리 있는 사람을 놓쳤다.

**조사 결과:** 1080p 원본 598프레임 전체를 같은 YOLO/ByteTrack 조건으로 비교했다.

| 항목 | 모델 입력 320 | 모델 입력 640 |
| --- | ---: | ---: |
| 사람 검출 프레임 | 356/598 | 598/598 |
| 사람 미검출 프레임 | 242 | 0 |
| ID 1 추적 프레임 | 319 | 585 |
| ID 1 최초 관측 시간 | 약 4.69초 | 약 0.22초 |

**해석:** 입력 축소로 원거리 사람의 검출에 필요한 영상 정보가 줄어든 것으로 판단했다.
이 영상에서는 모델 입력 640이 검출을 더 잘 유지했다.

**조치/상태:** 해당 영상의 이후 테스트는 `imgsz=640`을 선택했다.
기존 웹캠 프로그램 기본값 320을 바꾸지는 않았다.
시연 카메라에서도 참가 거리·구도별로 검증한 후 모델 입력을 정한다.

**근거:** [전체 영상 입력 크기 비교](video-test-20261006.md#동일-yolov8nbytetrack-비교),
Jetson `.runtime/video-20261006-141148-640/`.

### TS-VISION-003

**증상:** 모델 입력만 줄여서는 원본 디코딩 병목이 남았고, 원거리 검출도 나빠졌다.
원본 영상 자체를 축소하면 속도가 개선되는지 확인했다.

**조치:** 원본을 유지한 채 16:9의 960×540과 640×360 H.264 CRF 20 변환본을 생성했다.
기존 정규화 calibration을 적용하고 세 영상 모두 모델 입력 640으로 고정했다.
준비 5프레임 후 추적과 영상을 초기화해 전체 598프레임을 검사했다.
입력·검출·추적·ROI·통과 후보 계산은 측정에 포함하고, 준비·화면·결과 저장은 제외했다.
VNC 서비스는 활성 상태이며 Pi에는 연결하지 않았다.

| 항목 | 원본 1920×1080 HEVC | 960×540 H.264 | 640×360 H.264 |
| --- | ---: | ---: | ---: |
| 처리 FPS | 5.15 | 13.14 | 13.67 |
| 598프레임 처리 시간(초) | 116.06 | 45.50 | 43.74 |
| 프레임 읽기 평균(ms) | 117.27 | 1.64 | 0.94 |
| 순수 GPU 추론 평균(ms) | 57.75 | 57.32 | 57.39 |
| 사람 검출 프레임 | 598/598 | 594/598 | 580/598 |
| 추적 ID 1 프레임 | 585 | 572 | 569 |
| 결승선 통과 후보 수 | 1 | 1 | 1 |
| 후보 교차 시간(초) | 8.215 | 8.196 | 8.194 |
| 후보 확인 시간(초) | 8.261 | 8.220 | 8.237 |

**해석:** 960×540은 약 2.55배 빨라졌지만 GPU 추론 시간은 거의 같았다.
주로 읽기/디코딩 비용이 줄었다. 해상도와 HEVC→H.264 코덱을 함께 바꾼 비교이므로
속도 개선을 해상도 축소만의 결과로 표현하지 않는다. 원본 경로의 하드웨어 디코더 사용 여부도 확인 전이다.
960×540의 미검출 4프레임은 초반 약 0.153초 이내, 640×360의 18프레임은 약 0.305초 이내였다.

**결정:** 현재 영상 개발은 960×540 + 모델 입력 640을 사용한다.
640×360은 추가 속도 개선이 약 4%인 반면 검출 손실이 더 컸다.
한 사람 영상에서의 통과 후보 확인이며 최종 게임 판정·움직임 검증은 아니다.

**근거:** [변환 명령과 상세 결과](video-test-20261006.md#원본-해상도-변환과-전체-프레임-비교-2026-10-06),
로컬/Jetson `.runtime/resolution-comparison/report.json`.

### TS-VISION-004

**증상:** 첫 FFmpeg 변환본의 프레임 수가 원본 598에서 595로 줄었다.

**원인:** 기본 동기화 설정에서 가변 프레임 입력을 고정 약 59fps로 출력하며 일부 프레임이 제외됐다.
`ffprobe`로 595프레임을 확인했다. 변환본과 원본의 통과 시점을 공정하게 비교하려면 프레임 수를 보존해야 했다.

**조치:** `-vsync 0`으로 변환본을 다시 생성했다. 원본 파일은 변경하지 않았다.

**검증:** 두 변환본 모두 598프레임을 확인했다. 인코더 시간 단위 반올림 때문에
원본 비디오 스트림 약 10.062초와 변환본 약 10.068초 사이에 작은 차이는 남는다.
프레임 수 보존이 모든 타임스탬프의 비트 단위 일치를 뜻하지 않는다.

**재현/확인:** [변환 명령](video-test-20261006.md#원본-해상도-변환과-전체-프레임-비교-2026-10-06)의
명령을 사용하고 `ffprobe`의 `nb_frames`, `duration`, `avg_frame_rate`를 함께 비교한다.

### TS-VISION-005

**증상:** 960×540에서도 모든 약 59fps 원본 프레임을 차례로 검사하면 약 13fps 처리 속도 때문에
영상이 느리게 재생됐다. 실제 시간 기준으로 검출이 얼마나 자주 갱신되는지 보기 어려웠다.

**원인:** 영상 재생과 모델 검출이 한 순차 반복문에서 진행됐다.
전체 프레임 분석에는 유용하지만 원래 속도의 실시간 입력을 모사하는 방식은 아니었다.

**조치:** `jetson/realtime_video.py`를 추가했다.
재생은 미디어 시계 1배속으로 진행하고, 별도 검출 스레드는 최신 프레임만 처리한다.
처리할 프레임을 쌓지 않으며 화면도 늦어진 표시 프레임을 건너뛴다.
반복/재시작 때 추적·후보 상태를 초기화하고 이전 반복 결과는 표시하지 않는다.
이 기능은 오프라인 진단용이며 기존 웹캠 클라이언트·Pi 프로토콜은 변경하지 않았다.

**검증:** 초기 VNC 실행에서 첫 반복 평균 갱신 간격 약 211ms,
다음 반복은 약 136ms와 119ms였다. 다음 두 반복의 실제 재생 시간은 약 10.09초와 10.08초,
표시 수는 298/598과 301/598프레임(앱 기준 약 30fps)이었다.
각 반복에서 통과 후보가 1회 관측됐다. VNC 단말의 실제 수신/표시 FPS는 측정하지 않았다.
최신 값 교체·대기 중 종료·일시정지 시계 검사는 로컬과 Jetson에서 3개 통과했고,
기존 선 통과 단위 검사도 4개 통과했다.

**결론:** 실제 시간 재생은 확인했지만 매 프레임 검출이나 60fps 화면 출력을 구현한 것은 아니다.
검출 갱신 간격과 결과 지연도 구분해야 한다. 초기 로그의 결과 지연은 프레임 읽기 전 시각까지
포함했으며, 최종 버전에서는 실제 전달 시각을 기록하도록 수정했다.
이전 대화의 약 190~240ms 표본은 이 시각 변경 전후의 기준을 혼합해 확정 성능값으로 쓰지 않는다.
최종 버전의 지연 분포는 고정 조건으로 다시 측정한다.
화면에는 검출 갱신 간격·처리 시간·박스의 영상 시간 차이·앱 표시 FPS를 구분해 보여준다.
노란 박스는 이전 검출 결과이며 영상 시간 차이가 500ms 이상이면 숨긴다.

**근거:** [실시간 재생 실행법과 지표](game-camera-setup.md#원래-재생-속도에서-검출-간격-확인),
로컬 `.runtime/realtime-960x540-snapshot.jsonl`, Jetson `.runtime/realtime-960x540.jsonl`.
후자는 반복 실행 시 덮어쓰므로 다음 측정부터 실행별 파일 이름으로 보존한다.

### TS-VISION-006

**증상/재현:** 최적화 시작 전 `import tensorrt`는 성공했지만
`tensorrt.nptype(tensorrt.float32)`는 `AttributeError: module 'numpy' has no attribute 'bool'`로 실패했다.
TensorRT Python 8.0.1.6, NumPy 1.24.4 조합이다.

**원인:** 설치된 TensorRT의 자료형 매핑 함수는 사전을 만들 때 `np.bool`을 참조한다.
NumPy 1.24에서는 이 별칭이 제거돼 float32 변환에서도 오류가 발생했다.
현재 Ultralytics 엔진 로딩도 이 함수를 사용하므로 엔진 생성 후 Python 적용 전에 호환 대응이 필요하다.

**대응 확인:** 임시 프로세스에서만 `np.bool = bool`을 적용해 float32와 bool 변환이 성공하는 것을 확인했다.
초기 검사 당시에는 공용 실행 코드나 설치된 패키지를 수정하지 않았다.
아래 후속 진행에서 엔진 선택 진입점에 적용하고 실제 엔진 검출 결과까지 검증했다.

**변환 도구 준비:** ONNX 1.14.1과 protobuf 3.20.3의 aarch64/Python 3.8 휠을
Jetson `.runtime/trt-setup/wheels/`에 보관하고 `.runtime/trt-setup/vendor/`에 `--no-deps --target`으로 배치했다.
해당 프로세스에만 `PYTHONPATH`로 적용해 두 버전의 import를 확인했다.
기존 환경의 protobuf 3.18.0과 NumPy 1.24.4는 유지했다.

**후속 진행:** 사용자가 최적화를 다시 승인해 같은 입력 크기로 ONNX 내보내기와
TensorRT FP32/FP16 엔진 생성을 완료했다. `game/detector.py`는 오래된 TensorRT 엔진을
선택한 프로세스에만 별칭 호환 처리를 적용하고, 메타데이터의 고정 입력 크기를 읽어 전처리에 적용한다.
설치된 라이브러리 파일이나 기존 `.pt` 기본 경로는 변경하지 않았다.
원래 모델은 영상 입력 `1×3×384×640`인데 정적 엔진을 기본 정사각형으로 전처리하면 크기가
맞지 않으므로 엔진 입력을 자동 적용한다. 웹캠 `1×3×480×640`은 별도 엔진으로 생성한다.

**영상 검증:** 같은 598프레임에서 PyTorch 12.76fps, TensorRT FP32 15.49fps, FP16 18.53fps였다.
순수 추론 평균은 각각 57.63/42.94/32.01ms였다. 세 경우 모두 사람 검출 594프레임,
추적 ID 1 572프레임, 통과 후보 1회를 유지했다.
[엔진 생성·비교 상세 기록](jetson-engine-optimization.md).
웹캠·화면을 포함한 실제 지연과 다인/움직임 판정 검증은 이 영상 비교와 구분한다.

**웹캠·VNC 후속 검증:** 웹캠 480×640 입력의 FP16 엔진도 만들었다.
같은 입력 크기로 실제 카메라 각 120프레임을 순차 측정해 PyTorch 9.86fps→FP16 13.52fps,
순수 추론 평균 68.83→40.57ms를 확인했다. 다른 시점의 카메라 입력이므로 정확도 직접 비교는 아니다.
기존 웹캠 클라이언트의 FP16 오프라인 30프레임 실행도 확인했다.
VNC 영상 비교의 안정 두 반복은 평균 검출 갱신 간격 106.34→63.79ms,
프레임 전달→결과 완료 평균 지연 118.60→74.67ms였다.
초기 반복은 TS-VISION-007처럼 분리했다. 상세 조건과 한계는 엔진 최적화 문서에 기록했다.

### TS-VISION-007

**증상:** 세 번 반복하는 실시간 영상 비교에서 두 엔진 모두 첫 반복의 최대 앱 표시 지연이
약 1.25초(PyTorch), 1.40초(FP16)였다. 다음 반복의 최대 지연은 약 37~82ms 수준이었다.
모델 준비를 제외했다고 해도 첫 재생이 안정 구간과 같은 성능이라고 보기 어려웠다.

**조사/추정:** 기존 준비 실행은 첫 프레임만 다섯 번 사용했다.
이 영상 첫 프레임에서는 사람이 검출되지 않으므로 실제 후처리/추적 초기화 경로를
충분히 준비하지 못했을 가능성이 있다. 초기 디코더/메모리 준비 비용도 분리해 단정하지 않는다.

**조치:** 약 2초 위치의 프레임으로 준비 실행한 뒤 소스를 처음부터 다시 열고 첫 프레임을 읽는다.
모델 준비가 끝난 다음에 재생 시계를 시작하고 추적/후보 상태도 초기화한다.
뒤쪽 프레임을 읽을 수 없는 짧은 영상은 첫 프레임으로 준비한다.

**측정 원칙:** 첫 반복과 안정 반복을 구분하고, 준비 단계를 바꾼 결과는 이전 결과와 구분해 보관한다.
안정 구간 숫자로 최초 시작 지연이나 매 프레임 표시를 보장하지 않는다.
최종 FP16 실행 결과는 `.runtime/trt-benchmark/realtime-fp16-final.jsonl`에 남긴다.

**보완 후 관측:** 새 FP16 실행의 첫 반복에서도 최대 표시 지연 약 1.94초가 관측돼
준비 프레임 변경만으로 초기 지연을 해결하지 못했다. 다음 반복 평균 갱신 간격은 약 65/66ms로
안정됐고 최대 표시 지연은 약 121/79ms였다. 뒤쪽 프레임 준비가 단독 해결책이라고 판단하지 않는다.
초기 지연 원인은 추가 프로파일링 대상으로 남기며 최적화 완료 수치는 안정 구간과 구분한다.

**2026-10-07 웹캠 추가 조사:** 모델 준비 전에 잡은 첫 카메라 프레임을 준비 완료 뒤
검증에 전달해 시험 31회 검출인데 경과 약 30초가 표시되는 것을 확인했다.
웹캠은 준비 완료 뒤 새 프레임부터 전달하도록 수정했다. 서비스 재시작 뒤
검출 1038회/시험 경과 67.9초를 확인했다(640×480 웹캠, FP16 480×640,
MJPEG 최대 5Hz, 최근 300회 평균 간격 64.6ms 표본). 영상 재생의 초기 지연 해결이나
정확도·전체 카메라 지연 검증을 의미하지 않는다. 실제 두 사람 교차 정확도는 검증 전이다.
관련: [웹캠 검증](vision-validation.md), `jetson/web_server.py`.

## 추론 최적화 진행 순서 (영상 엔진 비교 완료)

Python 전체를 C++로 옮기기 전에, 엔진과 주변 처리 비용을 분리해서 개선한다.
PyTorch의 계산 비용이 큰 연산은 이미 C++/CUDA에서 실행되므로 언어 변경만으로
GPU 추론 시간이 크게 줄어든다고 가정하지 않는다.
[PyTorch C++ frontend 설명](https://docs.pytorch.org/cppdocs/frontend.html).

1. **호환 환경 확인:** 현재 장비의 TensorRT와 Python 바인딩, ONNX 변환 도구를 확인한다.
   2026-10-06 읽기 확인에서 TensorRT 라이브러리/개발 도구는 `8.0.1-1+cuda10.2`가 설치돼 있었다.
   기존 Python 3.8 환경에서 `import tensorrt`도 성공했고 버전은 `8.0.1.6`이었다.
   `/usr/src/tensorrt/bin/trtexec`도 확인했다. 해당 Python 환경의 ONNX와 PyCUDA 모듈은 없었다.
   ONNX 변환 도구 및 엔진 실행 경로를 정한 뒤 필요한 의존성만 준비한다.
   이번 문서 정리에서는 환경을 변경하거나 패키지를 설치하지 않았다.
   최신 TensorRT를 바로 설치하지 않고 현재 L4T/CUDA에 맞는 경로를 선택한다.
   [JetPack 4.6 구성](https://developer.nvidia.com/embedded/jetpack-sdk-46).
   이후 사용자가 Python 유지·엔진 최적화를 승인해 별도 폴더에 변환 도구를 준비했고,
   TensorRT/NumPy 호환 문제를 재현·임시 대응 확인했다(TS-VISION-006).
2. **기준선 고정:** 960×540 영상 + 현재 모델 입력 640, 웹캠 경로를 각각 측정한다.
   현재의 직사각형 전처리 실제 텐서 크기·letterbox·NMS 조건도 기록해 엔진 비교에 맞춘다.
   워밍업을 제외하고 같은 구간에서 추론·추적·전체 지연·갱신 간격의 평균/p95,
   원거리 검출·ID 유지·통과 후보·메모리·온도를 실행별 로그에 남긴다.
3. **TensorRT 비교:** 같은 모델을 ONNX로 변환하고 장비에서 batch 1 엔진을 만든다.
   FP32로 동등한 결과를 먼저 확인한 뒤 FP16의 속도와 검출 결과를 비교한다.
   엔진 단독 속도와 Python에서 추적·화면을 포함한 속도를 각각 측정한다.
   Python에서도 TensorRT 엔진을 호출할 수 있다.
   [TensorRT 8.0 계열 성능 지침](https://docs.nvidia.com/deeplearning/tensorrt/archives/tensorrt-803/pdf/TensorRT-Best-Practices.pdf).
4. **남은 비용 개선:** 프로파일 결과에 따라 전처리·CPU/GPU 전송·후처리·화면 표시 빈도와
   캡처 지연을 줄인다. 1080p 입력을 유지할 필요가 있을 때 하드웨어 디코딩 경로를 별도로 확인한다.
   C++ 전환은 CPU/Python 비용이 병목으로 남았을 때 해당 구간부터 검토한다.
5. **시연 조건 검증:** 실제 거리·다인·가림·빠른 통과·정지/손/몸 움직임과 장시간 실행,
   Jetson→Pi→MCU 전체 전달 지연을 확인해 최종 설정을 정한다.

기존 기본 모델은 PyTorch 경로이며, TensorRT는 `--model ...engine`으로 선택한다.
영상 FP32/FP16 엔진을 생성하고 위 결과를 확인했다. 향후 카메라·화면·다인 조건의 속도를
영상의 18.53fps로 보장하지 않는다. 새 검증 결과가 확인되면 상태와 근거를 갱신한다.

  사용자 표시 확인 결과는 유효하며 이 접속 문제와 구분한다.
- 조치: 직접 SSH 재시도, Pi에서 ping/웹 확인, ProxyJump 경유 SSH 확인을 실행했다.
  Jetson에 접속하지 못해 서비스를 재시작하거나 최신 기록을 Jetson 저장소에 동기화하지 못했다.
  확인되지 않은 상태에서 복귀 잠금을 해제하거나 완료를 주입하지 않았다.
- 원인/남은 일: 미확정. Jetson 로컬 전원/부하/서비스/네트워크 상태 확인 후 SSH·웹·연결기 복구,
  Pi HOME 확인과 저장소 동기화가 필요하다. 참고: `.runtime/game/controller.log` (Pi, Git 제외).

### TS-AUDIO-001

- 날짜/조건: 2026-10-08 사용자가 구호·총소리 MP3를 제공하고 Jetson USB 스피커 사용을 확인했다.
- 증상/근거: PulseAudio에는 USB와 보드 analog 출력이 모두 있었으며 기본 sink는 analog였다.
  USB 스피커에서 무음이 실제 발생했다고 확인한 것은 아니며, 출력 장치 선택의 불일치를 확인했다.
- 조치: USB를 기본 출력으로 지정하고 음소거를 해제했다. 연결기 서비스에도 USB PULSE_SINK와
  XDG_RUNTIME_DIR을 [설정](../tools/systemd/jetson-audio.conf)으로 지정했다.
  사용자 음원은 Jetson `.runtime/audio`에 보관하며 Git에서 제외했다.
- 기능: Pi --audio는 구호 완료 응답 후 FRONT를 요청하고, 확정된 새 탈락만 효과음을 요청한다.
  구호 재생 오류·30초 응답 누락 시 중단/뒤보기 복귀한다. 중지·종료·연결 해제 시 구호를 취소한다.
  재생 중 겹친 탈락은 효과음 하나로 합친다. 상세: [실행 문서](game-runtime.md).
- 검증: USB sink를 지정한 ffplay로 구호 약5.982초와 총소리 약1.992초 재생 명령 종료 코드0 확인.
  직접 청음은 하지 못했다. Pi C -O2 -Wall -Wextra -Werror 빌드 통과.
  실제 C/서버/연결기와 모의 재생기로 음원 완료 전 FRONT 차단, 이후 경기 진행·탈락·만료·중지
  통합 시험 통과. 기존 무음 경기 회귀 시험도 통과. 재생기 exit1에서 audio_error 중단과 HOME 복귀 통과.
- 시험 중 조치: 최초 모의 시험은 Pi 시험 환경의 연결기가 구버전이라 --audio-dir 인자를 거절했다.
  최신 연결기와 audio 모듈을 반영한 뒤 재시험해 통과했다. 실제 장치 통신 문제와 구분한다.
- 배포: Jetson 연결기를 재시작하고 대기 중인 Pi 20초 클라이언트를 --audio 포함 실행으로 교체했다.
  실제 START는 보내지 않았다. 남은 일: 실제 USB 청음, 음원 종료/모터 회전/정지 판정 동기화,
  총소리·LCD·DB 현장 경기 검증. 30초 무응답 경로와 재부팅 후 출력 유지 실물 시험은 미실행이다.
- 배포 후 최종 확인: Jetson 연결기 active, HEALTH ready, IDLE 적용 응답 확인.
  Pi는 --game --duration 20 --audio로 실행 중이나 STM REAR@OK가 오지 않아
  RECOVERY_TIMEOUT 상태로 자동 복귀 재시도 중이다. TCP 연결 잔존만으로 STM 응답 가능을
  확정하지 않았다. 사용자에게 STM 리셋/재연결과 USB 청음 확인을 요청했다.
