# 무궁화 꽃이 피었습니다 — 예상 질문과 답변

작성: 2026-10-12. 최신 11장 발표자료·6차 대본과 현재 저장소 기준.
답변은 첫 문장을 짧게 말하고, 추가 질문이 있을 때 근거를 설명한다. 현장 검증·정량 측정이 없는 항목은 완료된 사실로 답하지 않는다. 과거 설계 문서와 현재 동작이 다르면 현재 코드·게임 실행 문서를 우선한다.

## 2. 주제·독창성·실무 활용

### Q1. 왜 ‘무궁화 꽃이 피었습니다’를 선택했나요?

**짧은 답변:** 재미와 실무 활용 가능성을 함께 갖춘 IoT 서비스를 고민하면서 놀이공원의 체험형 놀이시설을 떠올렸습니다. 규칙이 익숙해 관객이 기능을 쉽게 이해하고, 인식·제어·통신·기록을 하나의 서비스로 연결하기 좋았습니다.

**추가 질문 대비:** 놀이공원에 이미 납품하거나 운영 중인 시스템은 아니다. 이번 구현은 체험형 IoT 서비스의 가능성을 보여주는 프로젝트다.

### Q2. 이미 있는 놀이인데 독창성은 어디에 있나요?

**짧은 답변:** 놀이의 규칙을 새로 만든 것은 아닙니다. 카메라의 움직임 관측과 인형 동작, 여러 화면의 현황 표시, 참가자별 기록을 연결해 하나의 자동 진행 흐름으로 구현한 점에 초점을 뒀습니다.

**추가 질문 대비:** 핵심 차별점은 박스 중심 이동만 보던 방식에서 관절 비교로 바꾼 것과, 여러 보드의 시간·상태를 Pi 중심으로 정리한 통합 구현이다. 기존 제품 대비 최초·유일하다는 주장은 하지 않는다.

### Q3. 놀이공원에서 어떤 업무에 활용할 수 있나요?

**짧은 답변:** 체험시설에서 참가자 등록, 진행 상태 표시, 결과 집계와 기록을 돕는 서비스로 발전시킬 수 있습니다. 운영자가 현황을 확인하고 반복 체험을 관리하는 데 활용하는 방향입니다.

**추가 질문 대비:** 현재 구현한 참가자 인식·장치 제어·결과 기록을 활용하는 방향이다. 발권·결제·입장 관리까지 구현한 것은 아니다.

### Q4. 당장 실제 시설에 설치할 수 있나요?

**짧은 답변:** 현재는 프로젝트 규모의 구현입니다. 실제 운영을 위해서는 조명과 가림, 여러 참가자의 교차 상황에서 판정 신뢰도를 검증하고, 장시간 동작과 장애 대응, 운영자 확인 절차를 보강해야 합니다.

**추가 질문 대비:** 시설 규모에 따른 카메라 배치, 장치 보호, 유지보수, 현장 개인정보 처리 정책도 설계해야 한다. 실제 산업 현장 적용 완료나 무인 운영 가능성을 보장하지 않는다.

### Q5. 카메라로 사람을 보면 개인정보 문제는 없나요?

**짧은 답변:** 현재 참가자는 얼굴이나 이름으로 식별하는 대신 경기 안의 추적 ID와 참가자 번호로 구분합니다. 실제 운영에서는 영상 저장 여부와 목적, 접근 권한과 보관 기간을 정해야 합니다.

**추가 질문 대비:** 개발 중 검증 영상이 있을 수 있으므로 “영상을 전혀 저장하지 않는다”고 단정하지 않는다. 얼굴 인식으로 신원을 알아내는 시스템으로 설명하지 않는다.

### Q6. 비용은 얼마나 들고 다른 장소에도 적용할 수 있나요?

**짧은 답변:** 경기 구역과 결승선, 통과 방향을 설정할 수 있어 장소 변경에 대응하는 구조입니다. 다만 최대 거리와 설치 조건을 보장하는 시험이나 정확한 총비용 산정은 아직 하지 않았습니다.

**추가 질문 대비:** 장비 구매비와 시설 설치·보호·유지비는 구분한다. 부품 명세와 실제 구매 내역 없이 금액을 추정해 답하지 않는다.

## 3. 장치 역할·통신·동기화

### Q7. 왜 Pi와 Jetson을 나눴나요? 한 대로 하면 안 되나요?

**짧은 답변:** 영상 AI 처리와 게임 진행 책임을 분리했습니다. Jetson은 영상에서 관측을 만들고, Pi는 경기 단계·시간·최종 결과를 관리합니다. 인식 처리와 장치 제어를 나눠 개발하고 확인하기 위한 선택입니다.

**추가 질문 대비:** 한 장치로 통합하는 것은 가능한 설계 대안이다. 이번 프로젝트에서 한 대로는 절대 불가능했다고 말하지 않는다. 네 장치가 상용화에도 반드시 필요하다는 뜻은 아니다.

### Q8. STM32와 Arduino를 둘 다 사용한 이유는 무엇인가요?

**짧은 답변:** STM32는 시작·중지 버튼, 인형 모터와 LED, 현장 LCD를 담당하고 Arduino는 떨어진 위치의 LCD 표시를 담당했습니다. 제어와 별도 위치의 표시를 구분한 구성입니다.

**추가 질문 대비:** 실제 서비스에서는 규모와 비용에 따라 장치 수를 줄일 수 있다. 이번 구성의 역할과 통신을 설명하는 것이 핵심이다.

### Q9. 움직인 사람을 Jetson이 발견하면 바로 탈락인가요?

**짧은 답변:** Jetson은 관측 후보를 보내고, 최종 결과는 Pi가 확정합니다. 현재 경기와 단계에서 나온 정보인지, 등록된 참가자인지, 이미 결과가 정해진 사람인지 확인합니다.

**추가 질문 대비:** 경기 ID·단계 토큰·카메라/구역 버전 등으로 이전 정보와 현재 정보를 구분한다. 같은 관측이 다시 와도 결과와 인원수가 중복 증가하지 않도록 처리한다.

### Q10. 어떻게 장치 간 시간을 맞췄나요?

**짧은 답변:** 각 LCD가 따로 시간을 줄이지 않고 Pi가 계산한 남은 시간을 전달받아 표시합니다. 회전이나 판정 시작도 응답을 확인한 뒤 다음 단계로 진행합니다.

**추가 질문 대비:** 단일 기준이므로 독립 타이머의 불일치를 줄이는 구조지만, 통신 지연이 0이거나 모든 화면이 물리적으로 같은 순간에 바뀐다는 보장은 아니다. 발표 애니메이션의 동시 갱신은 원리를 설명한 것이다.

### Q11. 인형 회전 완료는 센서로 실제 각도를 확인한 것인가요?

**짧은 답변:** 현재 발표에서 말하는 완료는 STM32 펌웨어의 회전 처리 완료 응답입니다. 별도 각도 센서로 실제 도달 위치를 측정했다고 설명하지는 않습니다.

**추가 질문 대비:** 실제 시설에서는 기구가 걸리거나 모터가 제대로 움직이지 않는 경우까지 검출할 수 있도록 위치 확인과 장애 감지를 보강하는 것이 필요하다. 관련 장의 작은 주석과 같은 범위로 답한다.

### Q12. TCP인데 데이터가 나눠 들어오는 문제는 왜 처리하나요?

**짧은 답변:** TCP는 데이터를 순서대로 전달하지만 한 번 읽은 데이터가 명령 하나와 같다는 보장은 없습니다. 줄 끝까지 모아 명령 단위로 처리하고 값도 확인합니다.

**추가 질문 대비:** 여러 명령이 한 번에 들어오는 경우도 처리 대상이다. Arduino의 정상 표시 후 응답과 TCP 전송 자체의 성공은 다른 확인 단계다.

### Q13. Bluetooth를 사용하는데 멀리 떨어진 곳에서도 가능한가요?

**짧은 답변:** 이번에는 별도 위치의 표시 장치 연결에 Bluetooth를 사용했습니다. 실제 통신 가능 거리는 주변 환경과 장치에 영향을 받으므로, 원거리 시설 전체를 연결할 수 있다고 주장하지 않습니다.

**추가 질문 대비:** 큰 시설에서는 유선망이나 시설의 무선망 등으로 표시 경로를 바꾸는 것이 확장 대안이다. 이번에 최대 거리나 대규모 무선 안정성을 측정한 것은 아니다.

### Q14. 통신이 끊기거나 응답이 오지 않으면 어떻게 되나요?

**짧은 답변:** 중요한 단계의 응답을 기다리고, 제한 시간 안에 완료되지 않으면 오류로 처리합니다. 연결 문맥이 바뀐 경우에도 기존 경기를 정상적으로 이어진 것처럼 취급하지 않습니다.

**추가 질문 대비:** 오류 시 중단·뒤보기 복귀를 요청하는 처리와 실제 장치가 복귀했다는 보장은 구분한다. 장치 통신 자체가 끊긴 상황에서 물리적 복귀까지 보장하지 않는다. 장시간 장애의 실장 검증은 별도 과제다.

## 4. 영상 판정·참가자·게임 규칙

### Q15. 사람의 움직임은 어떻게 판단하나요?

**짧은 답변:** 멈춰야 하는 단계가 적용될 때의 관절 위치를 기준으로 삼고, 이후 손목이나 몸의 관절이 얼마나 달라졌는지 비교합니다. 사람의 화면상 크기로 보정하고 변화가 여러 프레임에서 지속되는지 확인합니다.

**추가 질문 대비:** 같은 자세가 계속 조금씩 변하는 경우도 고정 기준 대비 비교한다. 매 프레임 직전 자세만 기준으로 삼는 방식으로 설명하지 않는다. 현재 포즈 모델은 YOLOv8n-pose이며, 8장의 FPS 표는 별도 YOLOv8n 사람 검출 비교다.

### Q16. 작은 흔들림도 탈락시키나요? 기준은 무엇인가요?

**짧은 답변:** 한 프레임의 작은 흔들림만으로 바로 탈락시키지는 않습니다. 관절 신뢰도, 몸 크기로 보정한 변화량, 변화가 이어지는 시간과 관측 횟수를 함께 봅니다.

**추가 질문 대비:** 현재 관절 후보 코드의 참고값은 신뢰도 0.5, 정규화 변화량 0.03, 최소 0.2초·3표본이다. 손목 한 곳의 지속 변화 또는 몸 관절 두 곳의 지지 조건을 사용한다. 0.03은 실제 거리 3cm가 아니라 기준 박스 높이에 대한 비율이며, 정답 정확도 3%도 아니다. 상세 값은 `jetson/game/pose_motion.py`를 기준으로 답하고 현장 보정의 필요성을 덧붙인다.

### Q17. 가려지거나 화면에서 사라지면 탈락인가요?

**짧은 답변:** 보이지 않는다는 이유만으로 즉시 움직였다고 판단하지 않습니다. 관절 비교가 어려우면 판단을 보류합니다. 다만 경기 제한 시간이 끝났는데 결과가 정해지지 않은 참가자는 시간 만료 규칙에 따라 탈락합니다.

**추가 질문 대비:** 보류는 통과나 정지 확인과 다르다. 장시간 가림과 재등장 후 ID 연결은 계속 검증해야 하는 한계다.

### Q18. 사람이 서로 교차해서 ID가 바뀌면 어떻게 하나요?

**짧은 답변:** 현재는 시작할 때 등록한 추적 ID를 기준으로 관리하고, 새 ID를 다른 참가자에게 임의로 연결하지 않습니다. 교차와 가림 뒤에 같은 사람을 안정적으로 유지하는 부분은 추가 검증·개선이 필요합니다.

**추가 질문 대비:** 얼굴 재식별로 동일인을 복구한다고 답하지 않는다. 검출 추적 ID와 경기의 참가자 번호는 구분한다. 모든 상황에서 ID 유지가 완벽하다고 주장하지 않는다.

### Q19. 뒤늦게 들어온 사람도 참가자가 되나요? 최대 몇 명인가요?

**짧은 답변:** 참가자는 경기 시작 시 구역 안에서 관측된 사람으로 고정합니다. 이후 들어온 사람은 자동 추가하지 않습니다. 현재 코드상 등록 상한은 32명이지만, 이것이 32명 실시간 판정 성능을 검증했다는 뜻은 아닙니다.

**추가 질문 대비:** 발표의 3명은 표시 예시다. 실용 최대 인원은 설치 공간·가림·해상도·처리 지연을 포함한 실제 다인 시험으로 정해야 한다.

### Q20. 결승선에 먼저 등장하거나 반대로 넘으면 통과인가요?

**짧은 답변:** 설정한 결승선과 도착 방향을 기준으로 이동을 확인합니다. 단순히 도착 쪽에 있다는 이유만으로 통과시키는 방식은 아닙니다. Pi에서도 통과를 반영할 수 있는 경기 단계인지 확인합니다.

**추가 질문 대비:** 경기 구역·유한 결승선·이동 방향·관측 연속성을 함께 고려한다. 긴 관측 공백 뒤의 위치 도약을 정상 통과로 단정하지 않는다.

### Q21. 3분이 끝나거나 중지 버튼을 누르면 어떻게 되나요?

**짧은 답변:** 기본 제한 시간은 3분이며, 전원 결과가 정해지면 먼저 종료됩니다. 제한 시간이 끝나면 미완료 참가자는 탈락합니다. 중지 버튼은 경기 중단으로 처리하며 남은 참가자를 임의로 모두 탈락시키지는 않습니다.

**추가 질문 대비:** 제한 시간은 설정 가능하다. 중단 후 다시 시작하면 새 경기다. 발표 애니메이션의 짧은 반복 주기를 실제 경기 시간 규칙으로 설명하지 않는다.

## 5. 트러블슈팅·성능·완성도

### Q22. 가장 어려웠던 점과 해결 방법은 무엇인가요?

**짧은 답변:** 여러 장치의 경기 상태를 맞추는 것, 팔만 움직이는 경우를 잡는 것, 지난 화면 처리로 생기는 지연이 핵심이었습니다. 각각 Pi 중심 상태 관리, 관절 기준 비교, FP16과 최신 프레임 처리로 개선했습니다.

**추가 질문 대비:** 시간·상태 분산은 초기 설계의 한계와 개선이다. 실제로 LCD 시계 불일치 사고를 재현한 것처럼 말하지 않는다. FP16 수치와 최신 프레임 처리의 효과를 합쳐 측정한 것처럼도 말하지 않는다.

### Q23. 12.76FPS에서 18.53FPS면 게임 전체가 1.45배 빨라진 건가요?

**짧은 답변:** 아닙니다. 동일 저장 영상의 사람 검출 모델 처리량 비교입니다. 화면 표시, 결과 파일 저장, Pi 통신을 제외했으며 현재 관절 게임 전체의 반응 속도 수치가 아닙니다.

**추가 질문 대비 — 숫자 카드:**

| 조건/항목 | PyTorch FP32 | TensorRT FP16 |
|---|---:|---:|
| 입력 영상 | 960×540, 598프레임 | 동일 |
| 모델·실제 모델 입력 | YOLOv8n, 1×3×384×640 | 동일 |
| 처리량 | 12.76FPS | 18.53FPS |
| 프레임 처리 평균 | 78.37ms | 53.97ms |
| 프레임 처리 p95 | 85.67ms | 56.44ms |
| 순수 추론 평균 | 57.63ms | 32.01ms |

프레임 처리 범위는 읽기·검출/추적·기하 계산이다. 준비 후 같은 영상으로 순차 실행했고 화면·저장·Pi통신은 제외했다. 평균/ p95 역시 실제 카메라 동작부터 최종 탈락 표시까지의 지연이 아니다. 처리량 약1.45배와 순수 추론 평균 약44% 감소를 혼동하지 않는다.

### Q24. FP16으로 바꾸면 정확도가 떨어지지 않나요? 정확도는 몇 %인가요?

**짧은 답변:** 계산 정밀도가 달라지므로 출력이 완전히 같다고 보장할 수는 없습니다. 해당 영상에서는 사람 검출·추적 프레임 수와 통과 후보 관측이 유지됐지만, 정답 주석을 붙인 전체 움직임 판정 정확도는 아직 제시하지 않았습니다.

**추가 질문 대비:** 두 경로 모두 사람 검출 594프레임, ID1 추적572프레임, 통과 후보1회였다. 이 관측 수가 정확도 %는 아니다. FP16 박스와 기존 박스의 IoU 평균 약0.9939도 정답 대비 정확도가 아니라 출력 일치도다. 다인·가림·거리·조명별 오탐/누락과 최종 지연을 함께 측정해야 한다.

### Q25. 웹 미리보기가 5FPS라면 판정도 5FPS인가요?

**짧은 답변:** 영상 분석, 웹 미리보기, Pi로 후보를 보내는 주기는 구분합니다. 미리보기는 화면을 보기 위한 출력이며 그 숫자를 그대로 AI 추론 FPS나 게임 전체 반응 속도로 보면 안 됩니다.

**추가 질문 대비:** 문서상 미리보기5FPS·후보 송신5Hz·DB 조회약2초는 서로 다른 주기다. 후보 송신 주기에 최대 약0.2초 대기가 붙을 수 있으며 추론·네트워크 지연은 별도다. 실제 전체 지연은 시간 기준을 맞춘 측정이 필요하다.

### Q26. 최신 프레임만 쓰면 중간 동작을 놓치지 않나요?

**짧은 답변:** 오래된 프레임을 계속 처리하는 지연을 줄이는 대신, 너무 짧은 동작은 놓칠 수 있는 절충이 있습니다. 지속 변화 확인과 함께 실제 동작 장면에서 누락·오탐과 지연을 비교해야 합니다.

**추가 질문 대비:** 최신 프레임 선택만으로 정확도도 항상 좋아진다고 주장하지 않는다. 처리량을 높이는 것과 공정한 최종 판정은 별개의 검증이다.

### Q27. DB가 끊기면 경기 기록이 사라지나요?

**짧은 답변:** Pi가 로컬 기록을 먼저 남기고 별도 저장기가 MariaDB에 반영합니다. DB 장애 때는 재시도하며, 다시 처리할 때 중복 기록이 생기지 않도록 버전과 키를 확인합니다.

**추가 질문 대비:** 웹은 마지막 DB 기록과 지연 상태를 표시한다. 로컬 디스크 쓰기 자체가 실패하면 정상 저장한 것처럼 계속 진행하지 않는다. 모든 전원 장애에서 무조건 무손실이라고 보장하지 않는다.

### Q28. 직접 만든 부분과 기존 기술을 사용한 부분은 무엇인가요?

**짧은 답변:** 사람 검출·관절 추정은 기존 YOLO 모델과 TensorRT를 활용했습니다. 저희는 경기 구역 설정, 관절 변화 후보 처리, 경기 상태와 최종 판정, 장치 명령·응답, LCD·웹·DB 연결을 구현했습니다.

**추가 질문 대비:** AI 모델을 처음부터 자체 학습했다고 말하지 않는다. 홍성록은 Pi·Jetson, 박정환은 STM32·Arduino를 담당했고 통신 규격을 맞춰 통합했다. 역할이 발표 분량과 동일한 것은 아니다.

### Q29. 실제로 무엇까지 확인했고 무엇이 남았나요?

**짧은 답변:** 구현 흐름과 장치 통신, 영상 처리 및 기록 경로를 나눠 확인했고, 확인한 장면과 조건을 기준으로 설명하고 있습니다. 다양한 사람·거리·조명·가림을 포괄하는 정확도, 장시간 운영과 전체 지연 검증은 더 필요합니다.

**추가 질문 대비:** 발표 웹의 움직이는 그림과 수치는 설명용이다. 이를 실물 연동 영상이나 실측 결과로 소개하지 않는다. 촬영 예정인 실제 시연 영상과 코드/통신 시험 결과를 구분해 보여준다. 현장 성공 횟수나 성공률은 실제 기록이 있을 때만 답한다.

### Q30. 다음에 하나만 개선한다면 무엇을 하겠나요?

**짧은 답변:** 실제 시설 적용을 생각하면 다인 교차와 가림 상황의 참가자 추적·판정 신뢰도를 먼저 검증하겠습니다. 같은 조건에서 오탐·누락과 최종 지연을 측정해 판정 기준과 운영자 확인 절차를 보완하고 싶습니다.

**추가 질문 대비:** 이미 완료한 개선과 향후 계획을 분리한다. 카메라 추가, 사람 재식별, 운영자 보정 기능 등은 검증 후 선택할 대안으로 설명한다.
